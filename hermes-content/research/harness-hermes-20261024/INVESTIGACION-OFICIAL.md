# Cómo opera Hermes: LLM, herramientas, delegación y memoria

**Consulta de documentación oficial: 24 de octubre de 2026.** Investigación documental únicamente; no describe ni verifica configuración local, agentes activos ni producción. Las cifras de capacidad abajo son valores/defaults publicados, no lecturas de una instalación concreta.

## Hallazgos

1. **Ciclo modelo → herramienta → resultado → modelo.** `AIAgent` arma el prompt y los esquemas de herramientas, llama al proveedor y mantiene el historial. Si la respuesta trae `tool_calls`, Hermes ejecuta el handler; una llamada va por el hilo principal y varias pueden correr concurrentemente (salvo herramientas interactivas). Agrega cada resultado como mensaje `tool` y vuelve a llamar al modelo; una respuesta textual final cierra el turno y persiste la sesión. Ancla: *Agent Loop Internals* → “Turn Lifecycle” y “Tool Execution”; extracto: “execute them, append results, loop back”. [Fuente oficial](https://hermes-agent.nousresearch.com/docs/developer-guide/agent-loop)

2. **Modelo, proveedor y harness son capas distintas.** El modelo identifica qué modelo de inferencia se solicita; el resolver del proveedor determina la ruta efectiva —proveedor, credenciales, `base_url` y modo/API—. El harness es la capa `AIAgent`: construye el prompt, adapta formatos de API, administra historial y herramientas, compresión, reintentos y fallback. Los modos API convergen en un formato interno común; intercambiar modelo/proveedor no sustituye la orquestación del harness. Anclas: *Agent Loop Internals* → “Core Responsibilities”, “API Modes”; *Provider Runtime Resolution* → “Resolution precedence” y “Output of runtime resolution”. [Agent loop](https://hermes-agent.nousresearch.com/docs/developer-guide/agent-loop) · [Provider runtime](https://hermes-agent.nousresearch.com/docs/developer-guide/provider-runtime)

3. **Aislar contexto no aísla archivos.** Un hijo empieza con conversación nueva: recibe el `goal` y `context` entregados por el padre, más los archivos de contexto del proyecto si hay workspace resuelto. Tiene sesión de terminal propia, pero por defecto comparte el directorio de trabajo del padre. El aislamiento de archivos requiere activar explícitamente `delegation.worktree_isolation`; por tanto, no debe inferirse de “contexto aislado” que cada hijo tenga checkout aislado. Anclas: *Subagent Delegation* → “How Subagent Context Works”, “Background process lifetime”, “Worktree Isolation”; extractos: “completely fresh conversation”, “share the parent's working directory”. [Fuente oficial](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation)

4. **Herramientas heredadas y rutas configurables.** Los hijos heredan los toolsets habilitados del padre y no pueden ampliar sus capacidades mediante `delegate_task`. Hay excepciones: por defecto un hijo hoja no puede delegar; también se restringen `clarify`, escritura en memoria compartida, `send_message` y `cronjob`. La configuración puede fijar un modelo/proveedor/endpoint para hijos; si no se fija, heredan el modelo y la ruta del padre. Anclas: *Subagent Delegation* → “Model Override”, “Inherited Tool Access”; *Provider Runtime Resolution* → “Resolution precedence”. [Delegación](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation) · [Resolución de proveedor](https://hermes-agent.nousresearch.com/docs/developer-guide/provider-runtime)

5. **Concurrencia y ciclo de vida son configurables.** La guía de delegación documenta un máximo por defecto de **10 tareas concurrentes**, configurable y sin techo rígido; exceder el valor configurado produce error, no truncamiento silencioso. Es una capacidad/default documentado, no una afirmación sobre el valor de una instalación específica. Cada hijo tiene presupuesto de iteraciones; el límite de tiempo de pared es desactivado por defecto y opera un monitor de falta de progreso. El trabajo de procesos de terminal pertenece al hijo y termina con su cierre; al padre vuelve el resumen final, no el historial completo. Anclas: *Subagent Delegation* → “Parallel Batch”, “Max Iterations”, “Child Timeout”, “Background process lifetime”; extracto: “10 tasks by default”. [Fuente oficial](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation)

6. **Memoria persistente no equivale a entrenamiento.** `MEMORY.md` y `USER.md` son almacenes acotados en disco que Hermes inyecta como snapshot congelado al inicio de sesión; las ediciones se guardan, pero la sesión actual no recibe el nuevo snapshot hasta reiniciar/nueva sesión. `session_search` permite recuperar contexto de conversaciones pasadas. El mecanismo documentado es persistencia y recuperación de texto en el contexto, no una actualización de pesos del LLM; la página no promete cómo cada proveedor retiene o usa datos enviados por API. Anclas: *Persistent Memory* → “How It Works”, “Frozen snapshot pattern”, “Memory Needs Session Boundaries”; extracto: “frozen snapshot at session start”. [Fuente oficial](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)

7. **Compresión y caché gestionan contexto y coste, con límites.** El compresor integrado hace resumen potencialmente con pérdida (*lossy summarization*); su umbral base es 50%, con piso de 75% para ventanas menores a 512K; la higiene de gateway es una capa separada, fija al 85%. Para Anthropic, la guía estima alrededor de 75% menos coste de tokens de entrada en conversaciones de varios turnos gracias a cachear el prefijo; es una descripción del mecanismo, no una garantía de factura. Tras comprimir, se invalida la región comprimida, pero sobrevive el caché del prompt de sistema. Anclas: *Context Compression and Caching* → “Dual Compression System”, “Parameter Details”, “Prompt Caching (Anthropic)”, “Cache-Aware Design Patterns”; extractos: “lossy summarization”, “~75%”. [Fuente oficial](https://hermes-agent.nousresearch.com/docs/developer-guide/context-compression-and-caching)
