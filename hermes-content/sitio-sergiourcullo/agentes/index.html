Automatización, agente o loop.

No son sinónimos. La pregunta no es “¿puedo poner IA?”, sino quién decide el próximo paso: tus reglas o el modelo.

Qué no hace

Un agente no vuelve inteligente un proceso mal definido. Puede elegir qué herramienta usar, pero no debería inventar precios, aprobar pagos ni decidir excepciones comerciales. La parte crítica sigue teniendo una regla y una persona responsable.

02

Clasificar no necesita un agente

Es un workflow con IA: la ruta ya está definida

Un mensaje como “necesito una página urgente para mi restaurante” no entra en un IF simple, pero tampoco pide un agente. Basic LLM Chain, conectado a OpenAI Chat Model, devuelve tres campos, y Structured Output Parser los valida contra un JSON Schema:

{
  "categoria": "web",
  "urgencia": "alta",
  "requiere_humano": true
}

Si la salida no cumple la estructura, el nodo falla. Si la cumple, todavía puede estar mal clasificada: probalo con mensajes reales antes de confiar.

Después, Switch revisa primero requiere_humano. Si es verdadero, Telegram / Send Message avisa a una persona; si no, la consulta va a web, automatización u otro. El modelo interpreta; tus reglas deciden la ruta.

03

Cuándo un agente sí ayuda

Cuando el modelo tiene que elegir qué herramienta usar

Consultar el CRM, buscar una respuesta en documentos o pedirle al cliente un dato que falta. Ahí el próximo paso no está escrito de antemano: lo elige el modelo. Eso es un AI Agent.

Dale sólo las herramientas que necesita, con el permiso mínimo: el CRM, sólo para leer. Cada herramienta de más es algo que puede hacer sin que nadie lo decida.

La pregunta correcta no es “¿dónde pongo el agente?”. Es “¿quién decide el próximo paso: mis reglas o el modelo?”.
04

Qué es un loop útil

Revisar hasta que un estado cambie, con límite y salida

# una sola ejecución por cobro
Webhook  llega un cobro nuevo
  ↓
HTTP Request  consulta su estado
  ↓
IF  status = paid
  ├─ true  → registrar y avisar
  └─ false → ¿ya van 6 intentos?
       ├─ no → Wait 10 minutos
       │       → volver a consultar
       └─ sí → Telegram avisa
               a una persona

Un loop sin tope puede gastar API o seguir para siempre. Acá cada cobro abre una sola ejecución y la cierra: si el pago entra, avisa una vez; si a los seis intentos sigue sin pagarse, Telegram le pasa el caso a una persona. No lo armes con un Schedule Trigger cada 10 minutos más un Wait de 10: las ejecuciones se superponen y, una vez pagado, cada corrida vuelve a avisar. Esperar también es lógica, no una pausa decorativa.

Aplicalo con criterio

La arquitectura correcta hace más que el modelo más nuevo.

Guardalo para el próximo flujo que armes. Si querés que mire tu caso, contame el proceso y te digo si alcanza un IF, te sirve un modelo que clasifica, necesitás un agente o te falta un loop.
